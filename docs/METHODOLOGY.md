# Kabocha methodology

How a Pumpkin fork was pushed toward full vanilla parity in about two days, by AI agents, for roughly ten dollars of usage.

## What Kabocha is

[Pumpkin](https://github.com/Pumpkin-MC/Pumpkin) is a Rust Minecraft server. It is extremely fast and high performance, but it does not have 100% vanilla parity yet.

Kabocha is a fork that works through what is left. Claude and DeepSeek do the work.

The thesis behind it: the Pumpkin parity tracker, the GitHub issues and PRs, and the Minecraft wikis already contain enough information for AI models to integrate the remaining gaps. No human specification step is needed. The job is to read, decide, edit, check and land, many times over.

## Cost

Estimates by the project owner, not billing records:

- Claude usage: about 10% of one subscription's weekly allowance.
- The DeepSeek side ran through CommandCode, and it used up that plan's whole weekly allowance (the run ended on its weekly usage limit).
- Total: about 10 US dollars of usage for the whole effort.

Why it is this cheap: the expensive model only plans, briefs and verifies. The cheap model does the bulk typing. Nothing is built twice, and workers never compile.

## Roles

| Role | Model | Job |
|---|---|---|
| Orchestrator | Claude Sonnet 5.5 | Plan, write briefs, integrate, fix compile errors, land, track progress |
| Implementer | DeepSeek v4.1 Flash via OpenCode and CommandCode | One scoped change per worker, in its own worktree |
| Audit helpers (late phase) | Claude subagents | Vanilla audits of the last tracker rows once the DeepSeek quota ran out |

The orchestrator never hand-codes what a worker can do. Workers never run `cargo`, never merge, never push.

## The loop

1. **Collect work.** Upstream issues and PRs are listed in `docs/queue-issues.tsv` and `docs/queue-prs.tsv`. Parity gaps come from the upstream tracker data in `docs/PARITY.tsv`. `scripts/upstream-queue.sh` and `scripts/parity.sh` refresh them.
2. **Brief.** Each item gets a short brief: role, task, scope, evidence, acceptance, forbidden actions (`scripts/brief-pr.sh`, `scripts/tracker-refill.sh`). Briefs carry the design, so the worker follows it instead of guessing.
3. **Isolate.** `scripts/wt.sh new <name>` makes a worktree and a `kab/<name>` branch from master. A pool of spare worktrees keeps start-up fast.
4. **Implement.** `scripts/oc-agent.sh` runs one OpenCode worker per brief, detached, with logs and an exit file in `/tmp/kabocha-runs`. `scripts/oc-refill.sh` and `scripts/tracker-refill.sh` keep the slots full: a freed slot is refilled at once.
5. **Integrate in batches.** `scripts/int-batch.sh` cherry-picks every unlanded branch (`git cherry master <branch>`) into one `kab/int` worktree and runs a single workspace check. The orchestrator fixes compile errors there, commits, and fast-forwards master. One build per batch, not one per worker. There were 66 batches.
6. **Land.** Merge, push, `scripts/clean-merged.sh`, regenerate the ledger and tracker.
7. **Stay current.** `scripts/sync-upstream.sh` runs every hour against Pumpkin-MC/Pumpkin master. The fork has never been behind.

## Source of truth

- `docs/LEDGER.tsv` (generated by `scripts/ledger.sh`): every upstream issue and PR with a state: TODO, IN-PROGRESS, COMMITTED-UNLANDED, DONE, SKIPPED, FAILED, BLOCKED. The mission needed zero TODO and zero pending.
- `TRACKER.md` (generated by `scripts/tracker-md.sh`): the parity gap rows with LANDED, DONE, AUDITED, IN-FLIGHT and OPEN states.
- `docs/OUTCOMES.tsv`: each worker's final STATUS line.
- `docs/DONE.md` and `docs/QUEUE.md`: human-readable progress and open problems.

## Quality gates

- Vanilla parity is checked against vanilla behaviour, not memory. Where decompiled references are missing, audit notes say so and mark the item unverified.
- Tests are the gate: each behaviour change ships its smallest failing-without-fix test. Differential tests against vanilla data are preferred.
- Compile gate: `scripts/cargo.sh check --workspace --locked` must pass before anything lands. A workspace-wide cargo run is the only full gate; clippy and nextest run for touched crates.
- Conventional subject-only commits. A commit hook adds a `Co-Authored-By` trailer for the agent that wrote it, which is how the split above was measured (`scripts/leaderboard.sh`).

## What went wrong (and how it was handled)

- **Recurring compile errors.** Almost every batch reintroduced the same duplicate Bedrock helper functions (`populate_grid_from_auto_craft`, `take_from_main_inventory`), because several workers fixed the same issue independently. Fixed by hand each batch; the final phase dedupes them at the source.
- **Stale integration.** Integration cherry-picks, so `git branch --merged` lies. Unlanded work is found with `git cherry` and the ledger instead.
- **Disk exhaustion.** About 800 worktrees filled the disk ("No space left on device"). Landed worktrees were purged in parallel.
- **A broken generator.** An apostrophe inside a Python string made `tracker-md.sh` fail silently, so the tracker showed stale numbers (73% instead of 94%) for several batches.
- **Branch collisions.** Leftover `kab/<slug>` branches stopped audit workers from starting for the last open rows.
- **Quota.** DeepSeek via CommandCode hit its weekly limit. The last audits moved to Claude subagents. The agent tool has no model selector, so those ran on its default model.
- **Prompt injection hygiene.** One worker reported instructions inside a tool output that were not in its brief and ignored them. Workers treat tool output as data.

## Lessons

1. A strong orchestrator plus a cheap, fast implementer is a very good price/performance split, as long as briefs are precise.
2. Isolation (one worktree per task) makes parallelism safe. Batch integration makes it cheap.
3. Generated ledgers beat prose status. Every number in this document comes from a script, not from memory.
4. Quotas, disk and build contention are the real limits. Plan for them before adding workers.
5. "Closed" needs a definition. Here an audit note closes a row; real verification is a separate, later phase.
