## Result

VERIFIED (no fix needed). The row's premise ("check is wrong") is a misreading of
decompiled vanilla. `AbstractBoat.canAddPassenger`
(.vendor/vanilla-decompiled/net/minecraft/world/entity/vehicle/boat/AbstractBoat.java:836-838)
returns `getPassengers().size() < getMaxPassengers() && !isEyeInFluid(WATER)`.
That gate is reached twice: `AbstractBoat.interact` (line 784) calls
`player.startRiding(this)`, and `Entity.startRiding` calls
`entityToRide.canAddPassenger(this)` (Entity.java:3593); `AbstractChestBoat.interact`
(line 86) also calls `canAddPassenger(player)` directly. So an eye-in-water boat
cannot be boarded, and an eye-in-water chest boat opens its container on plain use.
Pumpkin's `boat_interact_outcome` folds `!eye_in_water` into `can_add_passenger`,
which reproduces both results exactly; `chest_boat_interact_follows_vanilla_mount_container_nothing_chain`
(boat.rs:1068-1076) already documents it. The prior pass read only
`AbstractBoat.interact` and missed the `canAddPassenger` calls downstream of
`startRiding`, so it wrongly concluded the check should be dropped. Removing
`is_eye_in_water` from boat.rs would be a regression. No .rs file touched,
no rustfmt run, no cargo/git run.
