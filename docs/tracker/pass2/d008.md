FIXED (row 5, `can_place_at` duplication). Added a single private helper
`get_state_for_placement(world, block, pos, player, clicked_face) -> Option<VineLikeProperties>`
that mirrors vanilla `VineBlock.getStateForPlacement` (VineBlock.java:275-290): it starts from the
clicked state (existing vine) or the default state, walks the placer's nearest looking directions
(or the fixed click-face order when no player is available), attaches the first free face that
`canSupportAtFace`, and returns `None` when nothing attaches and the clicked block is not a vine.
`on_place` now just maps that to a state id (AIR when `None`), and `can_place_at` reuses it and
runs vanilla `BlockItem.canPlace` -> `canSurvive` (`canSurvive` = `hasFaces(getUpdatedState(...))`)
on the produced state. The context-free branch (`player` and `direction` both `None`) keeps the
existing `canSurvive` recompute. Behaviour change: with a placement context the old code checked
only whether *a* face could attach, ignoring existing face conflicts; it now validates the exact
state that `on_place` would place, matching vanilla.
