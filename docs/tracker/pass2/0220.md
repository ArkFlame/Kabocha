## Result

VERIFIED (false positive; no code change needed). The audit row assumed `/reload` runs the
`#minecraft:load` tag synchronously inside the reload listener, but that is not true for the
1.21 target. Decompiled vanilla
`.vendor/vanilla-decompiled/net/minecraft/server/ServerFunctionManager.java`:
- `tick()` (lines 39-49) runs the load tag only when `postReload` is set and gates the whole
  method on `server.tickRateManager().runsNormally()`.
- `postReload(...)` (lines 74-77) is called from the constructor and from `replaceLibrary(library)`
  (the reload path, lines 69-72); it only sets the `postReload` flag and refreshes the tick list,
  it does not execute the load tag.

So vanilla also defers `#minecraft:load` to the next normally-running tick, exactly like Pumpkin:
`server/mod.rs:1041-1049` marks the pending reload, and `server/mod.rs:1932-1940` consumes it and
runs it before `#minecraft:tick` inside `tick_worlds`, which the `/tick freeze` branch skips.
Startup uses the same pending path (`server/mod.rs:567-573`). The existing unit test
`data/datapack/mod.rs::load_tag_runs_once_per_pending_reload` already covers the coalescing seam.

The comment in `reload_datapacks` and the doc comment on `DatapackManager::mark_load_pending`
already describe this deferred behaviour, so no Rust file was touched (the reason the source doc
gave for leaving this open was only that `server/mod.rs` was outside that earlier unit, which does
not apply here). No `rustfmt` run because no `.rs` file changed. Kept the finding in this doc to
avoid touching `docs/LEARNINGS.md`, which is outside this unit; the earlier audit suggested
recording the vanilla contract there if desired.
