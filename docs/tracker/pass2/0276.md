Decompiled vanilla `ClientboundBlockEventPacket` (`.vendor/vanilla-decompiled/net/minecraft/network/protocol/game/ClientboundBlockEventPacket.java:28-40`) reads the action parameter with `input.readUnsignedByte()` and writes it with `output.writeByte(this.b1)`. So although `ChestBlockEntity.signalOpenCount` passes the viewer count as a Java `int`, the value is truncated to one byte ON THE WIRE in vanilla too. A count of 256 wraps to 0 in vanilla exactly as it does in Pumpkin's `new as u8` cast (`chest_like_block_entity.rs:344`).

Widening `add_synced_block_event` / `BlockEvent::data` / `OnSyncedBlockEventArgs::data` / `CBlockEvent::action_parameter` to i32 would make Pumpkin's wire format diverge from vanilla, which writes a single byte. The server-side `on_synced_block_event` handler (`chests.rs:673`) only acknowledges the event and does not consume the data, so there is no server-side truncation bug either. No parity gap exists; leaving the code as-is preserves vanilla behaviour. No .rs files touched, so no rustfmt run.
